# Persistent Technical Findings

This document preserves findings that explain the current design or prevent failed approaches from being repeated. It is not a chronological work log. The current scope and verification status are in [SPECIFICATION.md](SPECIFICATION.md).

## Memory Targeting and Compatibility

- Process addresses and pointer chains derived from a single session are not stable across launches or updates. A saved chain may fail after a restart and must not be the sole basis for a write. Discovery must confirm the correct object, its structure, and uniqueness.
- An FOV value alone is not enough to identify a target: the game may contain duplicates or nearby numeric values. Do not write when there are no candidates or multiple candidates, a read is incomplete, a timeout occurs, or code has changed.
- It is not safe to search for mouse sensitivity as an arbitrary float. In the supported build, verify the named `FloatOption` (`ctrl_sensitivity2`, `sensitivity`, `options.sensitivity`), its vtable, and the live value range. The previously tested `Options+0x1BF4` was not the correct target and must not be used.
- The profile must match the exact package/PE and expected instructions. Matching an old signature or an address from another version does not authorize a write.

## Current Port Profile

The 1.26.6501.0 x64 profile uses PE timestamp `0x6AFA31EC`, image size `0x1383E000`, Options vtable `0xF278F10`, FOV wrapper vtable `0xF0A0160`, sensitivity wrapper vtable `0xF0A0190`, and perspective wrapper vtable `0xF0A0250`. The live named option layouts and perspective slot `+0x28` match the previous build. The client stack is at `+0x5E8`, client game at `+0x1C8`, game stack at `+0x1DF8`, and ScreenView transition flag at `+0x480`. The transition virtual slot is at `+0x288` and the client stack getter at slot `+0x730`.

The MinecraftGame vtable method at slot `+0x10` still reaches the FPS update call at `0x8790DE`, targeting `0x8793B0`. A matching function prologue elsewhere is insufficient because unrelated functions share prologues. The native wheel and mouse event consumers and verified wheel delta context also retain their RVAs and bytes. Full Bright's producer and consumer are adjacent in two vtables and resolve to `0x5AED350` and `0x5AED800`. The producer still writes the same temporary light-texture fields, and the patched epilogue is unchanged.

Nametag's producer at `0x5397C90` stores the local player at `[RBP+0xB8]`. The own-player patch replaces the nine-byte compare/branch and resumes before the native `mov rax,[rbx]`. The HUD patch replaces the thirteen-byte null-test/set/or sequence. The metadata preference loads EDX from `[RBP+0x2F1C]`; preserve EDX and the following native `and dl,al`. The depth argument at `0x5950F9E` receives Actor+8 in RDI, and the consumer's selector at `0x57E41A9` controls both text and background materials.

Always day uses the leaf at `0x293F240` through Dimension virtual slot `+0xF8`. Brightness, sunrise, direction and sun-facing helpers retain their ancestor depths. The sky-colour helper at `0x212E1E0` has a `0x78`-byte frame. Its parent lies at leaf-entry offset `0x80`, or `0x90` after the bridge's two pushes. Return addresses point immediately after each native call. Temporary stars and angle stores use `[RBP+0x2CB0]` and `[RBP+0x2CB4]`. The cloud patch at `0x6737D33` preserves alpha, and its binding references `CloudColor` at `0xF564D36`.

The exact expected bytes, call contexts and bindings in `GameMod\*Profile.h` are the source of truth. Diagnostic counters establish callback execution; only corresponding live checks establish visible behavior.

Minecraft exposes the named sensitivity option as a normalized `0.0`-`1.0` value. Keep the verified live setting unchanged at normal FOV; during Zoom, raise the camera projection ratio `tan(current FOV / 2) / tan(normal FOV / 2)` to `SensitivityScalingStrength` before applying the existing `MouseSensitivity` multiplier. Use the original sensitivity as the baseline on every frame so reversing the transition retraces the same curve.

## Input and GameInput

- The current Zoom code identifies the named sensitivity wrapper but uses its field at `+0x18`. In a local 1.26.6501.0 world, this field stayed at `1.0` as the Camera sensitivity (mouse) slider moved from 50 to 76 and back to 50. A separate entry with key 1 inside the wrapper tracked `0.50 → 0.76 → 0.50`. The settings screen read that entry through the native keyed lookup, loading the float at entry `+0x14`. A successful write and restoration at wrapper `+0x18` therefore establishes neither a change in the slider value nor the actual angular response. The settings-screen call stack identifies a UI reader only. Gameplay consumption, binding lifetime and update cadence still need independent verification.
- The native mouse event consumer at RVA `0x427530` packs relative X and Y into 16-bit integer fields in a 20-byte input record. Several routines consume that queue. Filtering the pair at enqueue time would quantize fractional output before the game converts mouse motion into angular displacement.
- In the 1.26.6501.0 executable, the option registration constructs both `ctrl_spyglassdamp` and `options.spyglassdampen` and passes option ID `0x256` with a default of 0.5. Its native getter selects an entry by input mode. A candidate downstream routine at RVA `0x6DA5E10` accepts a pair of floats. One conditional path dispatches through the same virtual slot as that getter and applies a common multiplier to both components. The paths converge on a consumer at `0x6DA6050`. There are five direct calls to the outer routine. Matching a virtual slot alone does not identify the runtime receiver. Mouse origin, angular units and stationary update cadence remain unverified; these locations are read-only investigation leads.

- Live observation in a local 1.26.6501.0 world confirmed that the call at RVA `0x4E088F2` reaches the candidate on the main game thread. The caller reads a pair from an input accumulator at offset `+0x34`, clears it and passes the scaled pair to the callee. The caller also branches on an input-mode value. The debugger observed mode 1 with `(0, +0.868886)` during the rightward mouse test and `(+0.673299, 0)` during the upward test. The pair is ordered vertical then horizontal. Two runs with no intentional mouse movement stopped at the 30th and 120th calls, respectively, and sampled `(0, 0)` in mode 1. This establishes recurring updates at rest without measuring undisturbed frame cadence. The behavior when changing input modes still needs verification.
- In build 1.26.6501.0, the executable references the names `CameraInjectInputLookDeltaSystem` and `CameraInputTransformSystem` while constructing or registering systems. Both references prepare a string and its length. Neither reference identifies a mouse-only angular displacement or establishes that camera updates run while the mouse is stationary. A rotation filter needs those two properties to drain pending mouse input without affecting another camera source.

- Screen-aware shortcuts verify both player and shared game stacks. A shared menu must block shortcuts even if the player stack still contains a HUD. The exact getter bodies, constructors, names and vtable slots are verified before discovery.
- Stack discovery walks native 0x20-byte entries from the active count at `+0x88`, with scene pointers at entry `+0x8` and vector start `+0x18`. A mismatched count, changing snapshot, unknown relevant type or incomplete read denies shortcuts. The reader invokes no virtual methods and writes no screen objects.
- The native scene name follows scene `+0x40`, ScreenView `+0x50`, VisualTree root `+0x8` and its string `+0x20`. ScreenView `+0x480` is a transition flag, not an input passthrough flag. Transitioning screens deny shortcuts, including closing chat. Stable native debug/toast overlays may be skipped by exact name.
- The independently profiled cubemap background is accepted solely at the shared stack's bottom. Its fixed name, vtable and constant-false methods are checked; it cannot establish gameplay without a verified player HUD. Regression fixtures include the observed background/debug/toast topology.
- Screen state is re-read at each input filter, not cached from a render callback. A separate bounded heap scan verifies a unique live client and excludes both input/FOV scratch snapshots. Unknown or ambiguous state passes input through and blocks all shortcut actions. The low-level keyboard hook observes every configured shortcut even in chat, requiring release after returning to gameplay; the worker also samples held keys when shortcuts are blocked. Profile checks and isolated input/discovery tests pass. Configured C Zoom, typing C in chat, returning to gameplay, F6-F9 toggles and F10 detach were confirmed in a local 1.26.6501.0 game. Other text entry screens and keys held across transitions still require in-game verification.

- `WH_MOUSE_LL` delivers input synchronously to the thread that installed the hook and also captures movement outside the game. If that thread scans memory or sleeps, it can delay even the desktop cursor. Therefore, the global low-level mouse hook is not used; input is captured only on local game paths.
- Input callbacks and the `WH_KEYBOARD_LL` owning worker must not write diagnostics to disk. Zoom callbacks enqueue static events without waiting for diagnostic locks. The worker formats complete snapshots of diagnostic data and paths, then submits them to a bounded queue for a separate file writer; this applies to Zoom, Nametag, Always day, and Full Bright. The writer never reads mutable worker state. Full or contended queues and writer startup failure drop optional diagnostics without a synchronous fallback. Shutdown rejects new records and drains accepted records; keep the module loaded and pump messages until the writer thread has exited. The former per-reading mouse trace also queried screen state and device identity just for logging, so it was removed. Check the native screen allowlist only when the input could actually be filtered, while still reading it live before filtering.
- Once both Raw Input APIs have inline hooks, rescanning module imports adds no coverage, including for later-loaded modules. Window-message hooks target the game window's owning thread and follow owner changes instead of enumerating every system thread. Zoom interpolation uses `QueryPerformanceCounter` and a local high-resolution waitable timer; the worker's wait also wakes for queued messages. `GetTickCount64` plus `Sleep(1)` does not guarantee millisecond animation steps. Diagnostic formatting is deferred only while animation is advancing: a failed FOV compare-exchange can leave `transitionActive` set with restoration pending, and must not suppress diagnostic submission indefinitely. Hook maintenance is deferred during transitions, and the status overlay redraw rate is independent of the animation update rate. These changes pass isolated checks, including simulated blocked diagnostic writes and shutdown; smoothness still requires an in-game check.
- GameInput V2 returns `positionX` and `positionY` as cumulative relative coordinates for each device separately. Keep those coordinates unchanged: scaling and rounding cumulative totals can discard small per-reading deltas and make low-sensitivity camera motion step. Adjust the uniquely verified named sensitivity option using compare-and-swap, with a projection-based scale derived from `tan(FOV / 2)`. Restore only while the same option owner remains bound to the same value address and the option still contains the value written by the module.
- `wheelY` is cumulative device state, not an individual wheel event. Overwriting it with zero and then restoring the original constant created artificial hotbar scrolling even when the user had not moved the wheel. The correct fix preserves the original cumulative value and suppresses only the derived scroll event on verified game paths.
- GameInput V0 and V2 have different interfaces and structure layouts. Verify the correct version and specific read path; do not mix up vtable indexes or assume input passes through Windows messages.
- `WM_POINTERWHEEL`, like `WM_MOUSEWHEEL`, carries a signed delta in the high word of `wParam`. When forwarding it to Zoom, preserve the sign and partial steps, and leave the message unchanged when Zoom is inactive.
- `WH_KEYBOARD_LL` alone did not capture every in-game path for the Zoom key. Filtering must account for the input interfaces actually in use and verify that the key does not trigger an in-game action at the same time as Zoom.
- The full mouse-sensitivity lookup can take longer than a short Zoom press. Resolve the unique option during FOV preparation, retry failed discovery at intervals while idle, and revalidate the live slot, owner, and value when a Zoom session starts. Restore an unchanged binding directly. If fallback discovery finds the original binding, revalidate it before deciding how to restore it.
- The keyboard hook retains eligible press and release edges until the worker processes Zoom. A complete tap received between worker iterations applies the part of the configured easing curve covered by the hold and immediately starts restoration. Keep periodic hook maintenance behind Zoom input processing. The `time_ms` field in Zoom diagnostics records the event time, which allows measuring the interval from `zoom-key-down` to `zoom-transition-first-fov-write` even when the writer flushes both events together.

In 1.26.6501.0, a live Zoom scroll changed the FOV through the verified wheel filter. Desktop mouse response and camera smoothness still require dedicated live checks.

## Local Rendering

- The day-cycle calculation is shared by multiple calls. Changing its result globally also affects non-rendering uses; Always day therefore supplies noon only to approved rendering calls. The shared brightness calculation also requires validation of the parent-call context so the change does not affect other uses.
- The first set of direct calls brightened the sky but did not cover daylight on terrain. The light texture has a separate path with its own brightness calculation; modifying the texture's entire result would remove the distinction between sky and block lighting. Each path therefore requires separate profiling and verification.
- The sun/moon angle, star brightness, cloud colour, and sunrise/sunset colour are independent rendering inputs. Fixing only direct day-cycle calls leaves shared colour helpers and tail-call paths using the real day phase. Preserve cloud alpha and change only temporary rendering descriptions. The user reported moving/wrong-position sun and visible moon in Fancy graphics with the previous implementation (issue #22). Profile v5 covers additional shared rotation and camera paths and matches the saved supported image. Tests execute the complete native day-cycle instructions with relocated constants and an equivalent sine table: approved paths produce the same phase as native tick `6000`, partial tick `0`, across multiple days; disabled and foreign paths preserve the original phase. This does not establish the final visual result, which still requires an in-game retest.
- Full Bright should change only temporary parameters of the native light texture, not gamma, player effects, or saved lighting. Depth testing and geometry occlusion should remain unchanged.
- Nametag uses the game's original rendering path. Depth testing must apply to both text and background; do not change persistent actor state for it.
- Hidden-HUD Nametag has two independent render-only gates in the supported build. The actor-name producer at `0x5397E9E` combines the native local-player check with `Options::hideHud` (slot `0x2F8`, getter `0x5AFAD20`, option IDs `0x1A5` and `0x11A`). Bypassing this gate alone executes name preparation and depth selection but does not display the name. The temporary player-name metadata at `0x5394DC6` also masks the native in-game/splitscreen player-name preference (slots `0x330`/`0x340`, option IDs `0x1A7`/`0x1A8`) by the same HUD result. Preserve the preference and the preceding native restrictions; change only this temporary mask, never the shared Options getter or stored HUD value. `GameMod/NametagHudProfile.h` verifies both frames, calls, getters, and branch contexts.
- While HUD suppression is bypassed, the actor loop must include only the current native local player. At its exit (`0x5397F23`), retain suppression of the separate hovered-object label path (`0x5398846`) by continuing at native cleanup (`0x5398C0C`). Refresh the thread-local HUD/local-player context on every producer invocation so the next visible-HUD frame restores normal actor filtering. All five Nametag patches are coordinated and must remain owned until restoration and bridge draining succeed.

## Hooks, Restoration, and Evidence

- Before installation, verify the expected original bytes and page protection. Prepare and restore multiple related patches in a coordinated way; if another party has changed the code, refuse to overwrite it.
- Before freeing a bridge, prevent new callbacks, wait for those already running, and check that no game thread is executing instructions in the bridge. If restoration fails, the module must remain loaded to prevent execution from freed memory.
- MinHook's single-hook disable path must freeze threads with `ACTION_DISABLE` so instruction pointers in its relay/trampoline move back to the original function. The FPS teardown also checks the trampoline's entire committed region after disabling; a zero callback count alone cannot prove that region is unused.
- Isolated tests can execute the actual emitted x64 bridges on synthetic pages and verify the ABI, registers, flags, and restoration. They do not replace checking behavior in a real process or visually verifying the game.
- A prepared profile, installed hook, or increasing diagnostic counter does not by itself prove correct behavior. Always distinguish profile rejection, an executed callback, a passing test, and a confirmed in-game result.

## Dependencies

MinHook source is included in the repository under `GameMod\vendor\minhook`, including its license, and is built locally. Add another external dependency only after verifying its origin, version, license, sources, and transitive dependencies; do not use its precompiled DLLs or non-public code.
